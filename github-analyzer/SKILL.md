# GitHub 开源项目分析

你正在执行一次 GitHub 项目分析。目标是从用户分享的截图/链接/描述中识别出项目，然后给出一份**实用的评估报告**，帮助用户快速判断"这个项目对我有没有用、值不值得花时间"。

## 第零步：加载用户上下文

在启动子 agent 之前，先收集用户当前的工具环境，注入到每个子 agent 的 prompt 中：

1. 用 Bash 运行 `ls ~/.claude/skills/ 2>/dev/null` 获取已安装的 skill 列表
2. 用 Bash 运行 `ls ~/.claude/agents/ 2>/dev/null` 获取已安装的 agent 列表
3. 检查当前目录是否有 `项目开发日志.md`，如有提取项目上下文

将以上信息整理为一段 `用户环境摘要`（约 100 字），作为固定前缀注入每个子 agent 的 prompt 末尾。这样子 agent 才能真正评估"与用户现有工具的互补性"，而不是泛泛而谈。

## 第一步：识别项目

用户可能通过以下方式提供信息：

1. **GitHub 链接**：直接粘贴 `github.com/owner/repo` 格式的 URL → 直接提取 owner 和 repo 名
2. **截图**：Twitter/微博/公众号等社交媒体截图，包含 GitHub 项目页面 → 用视觉能力识别：
   - 项目名（通常在页面标题位置）
   - Stars 数
   - 项目描述
   - README 片段
   - 关键功能列表
3. **文字描述**：用户口述"一个叫 XXX 的项目，可以YYY" → 提取关键词搜索

**如果信息不够确定**，用 AskUserQuestion 让用户确认项目名和 GitHub 地址。

## 第二步：并行信息收集

启动 2-3 个子 Agent 并行收集信息。每个子 Agent 的 prompt 必须完全自包含（子 agent 没有会话上下文）。

**重要**：优先使用 `gh api` 而非 `curl`，因为 `gh api` 已认证（5000次/小时 vs 未认证 60次/小时），且支持 `--jq` 直接过滤字段。

### 子 Agent 1 — 项目基本面

```markdown
## 任务
调研 GitHub 项目 {owner}/{repo} 的基本面信息。

## 收集内容
1. 用 WebSearch 搜索项目名 + 关键词，了解项目定位和社区评价
2. 用 Bash 运行: gh api repos/{owner}/{repo} --jq '{name, description, stargazers_count, forks_count, open_issues_count, language, license: .license.spdx_id, created_at, pushed_at, topics}' 获取基本信息
3. 用 Bash 运行: gh api repos/{owner}/{repo}/readme --jq '.content' | base64 -d 获取 README 内容
4. 用 Bash 运行: gh api repos/{owner}/{repo}/commits?per_page=5 --jq '.[] | .commit.author.date' 检查最近提交活跃度
5. 用 Bash 运行: gh api repos/{owner}/{repo}/contributors?per_page=10 --jq '.[] | .login' 查看贡献者

## 输出要求
用以下格式输出：
- **项目名**:
- **定位**: 一句话说明这个项目是什么、解决什么问题
- **Star数**:
- **Fork数**:
- **最近更新**:
- **活跃度评估**: 活跃/一般/不活跃
- **License**:
- **主要语言**:
- **核心功能列表**: 3-8 个关键功能点
- **安装方式**: 怎么装
- **依赖/系统要求**: 有什么前置条件
- **贡献者分布**: 个人项目/小团队/大公司/社区（附贡献者数量）
- **README 摘要**: README 的核心内容概括（300字以内）

## 用户环境
{用户环境摘要}
```

### 子 Agent 2 — 社区与生态

```markdown
## 任务
调研 GitHub 项目 {owner}/{repo} 的社区评价和生态系统。

## 收集内容
1. 用 WebSearch 搜索 "{repo_name} review" / "{repo_name} 怎么样" / "{repo_name} 替代品"
2. 搜索 "{repo_name} site:reddit.com" 了解用户真实反馈
3. 搜索 "{repo_name} site:v2ex.com" 或 "{repo_name} site:zhihu.com"（如果是中文社区项目）
4. 用 WebSearch 搜索同类竞品："与 {repo_name} 类似的工具"
5. 用 Bash 运行: gh api repos/{owner}/{repo}/issues?state=open&per_page=5 --jq '.[] | "- " + .title' 查看常见问题

## 输出要求
- **社区口碑**: 正面/中性/负面，附典型评价
- **常见问题**: Issues 中高频出现的 2-3 个问题
- **适用场景**: 这个项目最适合什么人、什么场景
- **不适用场景**: 什么人/场景不该用这个
- **中文社区讨论**: 如果有中文讨论，概括主要观点

## 竞品对比（至少找 2 个竞品）
用表格对比：
| 维度 | 本项目 | 竞品1 | 竞品2 |
|------|--------|-------|-------|
| Star 数 | | | |
| 最近更新 | | | |
| 安装难度 | | | |
| 核心差异点 | | | |
| 适合谁 | | | |

结论：本项目相比竞品的独特优势是什么

## 用户环境
{用户环境摘要}
```

### 子 Agent 3（可选）— 技术深度分析

只在以下情况启动：
- 项目 Star > 5k（说明项目有一定复杂度，降低阈值让优质小项目也能被深入分析）
- 用户明确要求技术评估
- 项目是框架/SDK/工具链类（需要评估集成难度）
- Star 少但用户特别关注的项目

```markdown
## 任务
对 GitHub 项目 {owner}/{repo} 进行技术深度分析。

## 收集内容
1. 用 Bash 运行: gh api repos/{owner}/{repo}/contents/ --jq '.[] | "\(.type)\t\(.name)"' 查看目录结构
2. 查看依赖文件：gh api repos/{owner}/{repo}/contents/package.json --jq '.content' | base64 -d（或 requirements.txt / Cargo.toml 等）
3. 用 Bash 运行: gh api repos/{owner}/{repo}/contents/.github/workflows --jq '.[].name' 2>/dev/null 检查 CI/CD
4. 用 Bash 运行: gh api repos/{owner}/{repo}/contributors?per_page=10 --jq '.[] | "\(.login): \(.contributions)"' 查看贡献分布

## 输出要求
- **架构复杂度**: 简单/中等/复杂
- **代码质量信号**: 有无测试、有无 CI、文档质量
- **集成难度**: 容易/中等/困难（安装步骤数、依赖数量）
- **二次开发友好度**: 好/一般/差
- **维护团队**: 个人项目/小团队/大公司/社区
- **API/MCP/插件生态**: 是否提供接口方便扩展

## 用户环境
{用户环境摘要}
```

## 第三步：生成评估报告

等所有子 Agent 返回结果后，综合生成报告。用中文输出。

### 综合评分（满分 10 分）

| 维度 | 分数 | 说明 |
|------|------|------|
| 需求相关度 | /10 | 与用户当前工作场景的匹配程度 |
| 项目成熟度 | /10 | 维护活跃度、贡献者分散度、Issue 处理质量 |
| 安装便捷度 | /10 | 越容易分越高，一条命令 10 分，需编译配置 3-5 分 |
| 现有体系互补性 | /10 | 与用户已装 skill/工具 的重叠度，互补越高分越高 |
| 长期维护信心 | /10 | 贡献者分散度、商业模式可持续性 |
| **加权总分** | **/10** | 上述五项均值 |

### 报告格式

```markdown
# {项目名} 分析报告

## 一句话结论
{用 15 个字以内说明：这个项目对你有没有用}

## 项目概览
- **定位**：{一句话}
- **Stars**：{数字} | **Forks**：{数字} | **语言**：{主语言}
- **活跃度**：{活跃/一般/不活跃} — {上次更新时间}
- **License**：{协议类型}

## 核心功能
1. {功能1}
2. {功能2}
...

## 评估结果

### 有用程度：{非常高 / 高 / 中 / 低 / 无用}

### 综合评分
| 维度 | 分数 |
|------|------|
| 需求相关度 | /10 |
| 项目成熟度 | /10 |
| 安装便捷度 | /10 |
| 现有体系互补性 | /10 |
| 长期维护信心 | /10 |
| **加权总分** | **/10** |

### 理由
- **亮点**：{2-3 个值得关注的点}
- **风险**：{1-2 个需要注意的问题}
- **与你现有工具的互补性**：{和你已安装的 skill/工具 的关系，说明重叠了什么、互补了什么}

### 竞品对比
| 维度 | {项目名} | {竞品1} | {竞品2} |
|------|----------|---------|---------|
| Star 数 | ... | ... | ... |
| 安装难度 | ... | ... | ... |
| 核心差异 | ... | ... | ... |

## 建议
**推荐 / 可选 / 不推荐** — {一句话原因}

### 如果安装
1. {具体安装命令}
2. {配置要点}
3. {注意事项}

### 如果不装
{替代方案或原因}
```

## 第四步：用户确认

用 AskUserQuestion 问用户：
1. 是否需要安装推荐的项目？
2. 是否需要更深入地分析某个方面？
3. 是否有其他项目想一起分析？

## 第五步：汇总对比（仅在分析 3 个以上项目时触发）

当用户一次性要求分析多个项目时，所有项目分析完成后输出汇总排序表：

```markdown
## 项目汇总排序

| 排名 | 项目 | ⭐ | 总分 | 建议 | 一句话理由 |
|------|------|-----|------|------|-----------|
| 1 | xxx | xxk | 8.5 | 推荐 | ... |
| 2 | xxx | xxk | 7.2 | 可选 | ... |

### 行动建议
- **立即安装**：总分 > 8 且安装简单的
- **观察等待**：总分 6-8 或还在 alpha/preview 阶段的
- **暂不考虑**：总分 < 6 或与现有体系高度重叠的
```

## 注意事项

- **信息来源优先级**：GitHub API 数据 > README 内容 > 社区搜索 > 模型知识。优先用实时数据，不要只靠模型已有知识。
- **不要回避负面信息**：如果项目有安全问题、维权争议、已停止维护等，直接指出。
- **分析要有针对性**：结合用户已加载的环境摘要，不要给出泛泛的评价。
- **控制篇幅**：单个项目分析报告控制在 500-800 字，重点突出可操作性。
- **多项目场景**：如果用户一次分享了多个项目（比如多张截图），先逐个识别，再统一分析，最后给出汇总排序表。
- **Star 少不等于差**：很多高质量的个人 skill 只有几十到几百 star，不要因为数字低就敷衍分析。重点看项目是否精准匹配用户需求。
- **技术栈判断**：子 Agent 3 的启动阈值从 10k 降到 5k，且用户特别关注的项目无论 star 数多少都应启动技术分析。
